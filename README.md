## 项目简介

MoonBit 的核心卖点是「一份源码，四个后端」：wasm、wasm-gc、js、native。
四个后端是彼此独立的实现，同一段代码在边界值上可能给出不同结果：
NaN 的符号位、`-2147483648 / -1` 是回绕还是终止、`1e21` 打印成 `1e+21` 还是 `1e21`、
代理对字符按码元还是按码点计数。

`moon test` 在每个后端上独立判断「结果是否符合预期」，它回答的是**对不对**。
「四个后端算的是不是同一个东西」是**另一个问题**：测试断言通常只覆盖
「数值落在容差内」「结果是个 NaN」这类性质，而位模式、打印格式、NaN 的符号位
往往不在断言范围内——四份输出各不相同，四份测试却全部通过。

MoonDiff 补的就是这一格。工作分三步：在多个后端上执行同一份程序；
把每一步的结果规范化成**只含 ASCII 的转录**；逐字节比对，定位到
「第几步、哪个原语、哪种值」不同，再自动收缩成最小反例并**复跑确认**。

更进一步，它不止说「不一样」，而是给出**裁定**：有条款就引出条款原文，
没条款就只报差异并指出规范缺哪一句，条款写明由实现自选的就判为不是缺陷。
裁定分四档，见「具体案例」一节。

项目本身不引入任何第三方依赖，全部逻辑由 MoonBit 明文实现，
因此**工具自身也能在四个后端上跑出完全相同的报告**——
报告里指出别人哪里不一致，得先保证自己不是那个不一致的来源。

## 项目方向与通用性说明

**方向**：MoonBit 生态中的「可检验性基础设施」（test & verification infrastructure）。

通用性体现在两个层面：**跟被测库无关**（针对的是原语语义——整数除法与取模、位宽边界、
浮点格式化、字符串码元/码点、编码往返；这些是所有包共用的底层行为，不随具体库而变），
**跟后端数量无关**（矩阵是运行时探测的，缺 C 编译器的机器上 `native` 自动标为
`unavailable` 并跳过，装上后自动进入矩阵；仓库 CI 在 Linux runner 上跑满四个后端，
所以「四后端」不是声明，是每次提交都被验证的事实）。

### 你不用写指令语言

用户写的是**普通 MoonBit**，不是本项目的语言。探针就是普通源码——`import` 真实包、
调用真实函数、`println` 结果，工具负责在多后端执行并逐字节比对 stdout：

```moonbit
fn case_bigint_mul() -> Unit {
  let a = @bigint.BigInt::from_string("123456789012345678901234567890")
  let b = @bigint.BigInt::from_string("-987654321098765432109876543210")
  emit("bigint-mul", (a * b).to_string())
}
```

`probes/moon.pkg` 里**没有** `wuhaiting321/moondiff`——探针不依赖本项目任何代码。
这是一条硬约束：探针能跑通，就说明工具不靠自家那套表示也能工作。接入自己的包只要三步：
在 `probes/moon.pkg` 加 import、在 `probes/main.mbt` 加一个 `match` 分支、
跑 `bash scripts/source-probe.sh --update` 记录基线。

**那套「指令语言」是工具的内部表示，不是交给用户写的接口。** 生成器产出它、
收缩器改写它、裁定器读它——这三件事都需要一个可枚举、可静态分析的直线程序表示。
用源码文本做不到：删一条语句要先解析整棵语法树，还得保证删完仍能编译，
而直线程序里「删掉一条不参与分歧的指令」可以直接判定。
仓库里 `examples/*.json` 是工具生成后存档的最小反例，不是要求用户手写的格式。

## 预期使用场景

### 场景一：发布前的一致性自查

一个数值 / 编解码 / 文本处理包准备发布，`moon test` 在四个后端上全绿。
发布前跑一次 `bash scripts/source-probe.sh`：全部 `PASS` 则四个后端的输出逐字节相同；
出现 `DIVERGENT` 直接给出用例名与两侧取值；出现 `ABORT` 则某个后端在途中崩溃。
这一步把「应该是一致的」变成「查过，是一致的」。

### 场景二：工具链或核心库升级后的回归

MoonBit 迭代很快，一次优化（常量折叠、内联、指令选择）就可能让某个后端在边界值上改变行为。
把 MoonDiff 挂进 CI，基线在 `tests/` 里入册：已知差异不反复刷屏，**新增差异立刻报警**，
且报告写明是哪一种值、哪一位不同。项目自己的 CI 就是这么跑的。

### 场景三：教学与规范讨论

「`-2147483648 / -1` 到底应该是什么结果？」这类问题用文字讨论容易各执一词。
MoonDiff 给出三样东西：差在哪、有没有条款管、条款原文是什么——而不是替规范下判断。
完整输出见 `docs/CASES.md` 案例 B；用仓库里 3 条指令的
`examples/min-div-overflow.json` 就能复现整条证据链。

### 场景四：包生态的横向体检

把若干已发布包的公开 API 写成源码探针，可以批量得到一张「生态一致性体检表」，
找出哪些包在哪个后端上有隐患——目前已完成 `BigInt` / `Double` / `String` / 编码
四个包、30 个用例，规模化是后续工作。这是 MoonDiff 作为**基础设施**而非单点工具的长期价值。

## 拟实现的核心功能

- **源码探针（不用学新语言）**：30 个探针覆盖 `BigInt`、`Double`、`String` 与
  UTF-8 / ASCII / Base64 编码，状态分 `PASS` / `DIVERGENT` / `ABORT` / `unavailable`
  四种——缺工具链时**不冒充 PASS**。
- **规格程序（工具内部表示，不需要手写）**：寄存器化直线程序，54 条原语（32/64 位整数、
  双精度浮点、六种转换、字符串、数组），每条指令对应一个明确的核心库操作；
  生成、收缩、裁定三件事都建立在这个可静态分析的表示上。
- **不丢位的编解码与规范化**：程序序列化为单行 JSON，64 位整数走十进制字符串、
  浮点走 16 位十六进制位串；结果渲染成纯 ASCII 规范形式（整数用补码、浮点用品模式、
  字符串带码元数/码点数），不同终端与编码环境下都能逐字节比对。
- **参照解释器**：解释器自身不做算术，只把每条指令转发给宿主原语，
  因此差异必然来自后端而不是来自工具。
- **三种比较档位**：`bit-exact`（只看位模式）、`strict`（位模式 + 宿主格式化）、
  `semantic`（折叠 NaN 载荷与 ±0），用于在「漏报」与「噪声」之间取舍。
- **差异定位与终止性识别**：给出首处分歧的步号、原语名、两侧原文；
  某后端 trap 导致转录缺少结束哨兵时单独识别为 `ABORT`，而不是报成「取值不同」。
- **确定性生成器与覆盖引导语料库**：xorshift64* 伪随机源，同一种子在任何后端给出同一序列；
  常量池刻意含 ±0、±inf、NaN、次正规数、整数上下界、代理对字符；以「原语 + 分支」为边
  只保留带来新边的输入，避免语料爆炸。
- **结构化收缩 + 复跑验证**：基于反向依赖闭包把几百条指令压到 3–5 条。删除是否安全
  可以静态判定（直线程序的删除是语义空操作），但工具不拿这个论证当结论——收缩之后会
  **把更小的程序再交给同一批后端跑一遍**，比对后端集合、终止集合、分歧原语与两侧取值，
  输出 `verified: reproduce` 或 `NOT-REPRODUCED` 及具体原因。
- **四档裁定，且出处进类型**：`SPEC-VIOLATION`（有条款要求某个值，某后端给了别的值）、
  `IMPLEMENTATION-FREEDOM`（条款明文把选择权留给实现）、`UNSPECIFIED-DIVERGENCE`
  （查过最接近的条款、其中没有规定）、`UNDETERMINED`（缺依据就承认判不了）。
  `Source` 只能由校验过非空的构造函数生成，且是 `Violation` 的**必填参数**——
  **没有条款原文的违规裁定在编译期就写不出来**。
- **手工探针电池与常量折叠电池**：8 组固定边界探针（浮点取余、除零、NaN 运算、
  转换越界、64/32 位溢出、Unicode、次正规数）永远可复现；24 条源码级常量表达式
  专抓「只在编译期折叠才出现」的差异。
- **回归基线与自举自检**：已知差异入册（`tests/`），CI 只对新增差异报警；
  `scripts/selfcheck.sh` 把工具自己送进矩阵，验证 `stats` / `matrix` / `shrink` / `gen`
  在四个后端上输出逐字节一致。
- **编排脚本**：`matrix.sh` 探测可用后端并汇总矩阵、`shrink.sh` 收缩并复跑、
  `source-probe.sh` 跑源码探针、`coverage.sh` 现算接口触达、`localize.py` 二分崩溃点。
- **测试与文档**：50 个单元测试覆盖编码、编解码往返、解释器确定性、随机源确定性、
  依赖闭包、四档裁定边界与收缩复跑的五项比较。

## 具体案例

`docs/CASES.md` 先用**一次完整运行**（矩阵 → 归因 → 裁定三段原始输出）说明机制怎么跑，
再给四个案例，每个都含原始输出、条款原文、复现命令与逐条边界。这里只给结论：

| # | 对象 | 结果 | 裁定 |
| --- | --- | --- | --- |
| A | `BigInt` 60 位大数乘法 | 四后端逐字节相同 | 无差异，不进任何一档 |
| B | `-2147483648 / -1` | wasm / wasm-gc / native 终止，js 回绕 | `UNSPECIFIED-DIVERGENCE` |
| C | 常量折叠后的 NaN 符号位 | wasm / wasm-gc / native 为负 NaN，js 为正 NaN | `IMPLEMENTATION-FREEDOM` |
| D | `String` 长度语义（`"a😀中"`） | 四后端一致：`length()`=4（码元）、`to_array()`=3（码点）、切片按码元 | 一致但**不等于**正确 |

**案例 A 是负结果，仍然写出来**：它证明工具在真实库上跑得通、能比、能下结论，
而不是只会在自造探针上找差异。它不构成「BigInt 正确」的证据。

**案例 B 与 C 的区别是整个裁定层的核心**：B 是规范**缺了一格**（`Div` 条目只写
「除数为 0 时 panic」，对商不可表示一字未提，`builtin/intrinsics.mbt:298-309`），
所以只报不一致、不指认违规方；C 是规范**写明由实现自选**（IEEE 754-2019 §6.2.3，
以及 wasm 规范 NaN propagation 的 "non-deterministic"），所以判为不是缺陷。
把这两者混为一谈，是差分工具最常见的两种错法。

**这一条为什么只报不一致、不判违规**：`Add` / `Sub` / `Mul` 三条**明文**写回绕，
`Div` 条目没有——从「加法回绕」推到「除法也该回绕」是推断，不是引用，
而指控需要引用。所以只给两件能举证的事：四份输出不同（可复现）、
规范缺这一条（可核对），不替规范选一边。上游 issue 的诉求也相应地是
「请补规定或确认设计」，正文见 `docs/UPSTREAM_ISSUE.md`。

**最小反例的复跑是实测的，不是承诺**：`probe:int-overflow` 从 9 条指令收缩到 3 条，
再把更小的程序重新交给同一批后端执行，比对后端集合、终止集合、分歧原语与两侧取值，
输出 `verified: reproduce`；把目标步故意钉错、让 trap 被收缩掉时判 `NOT-REPRODUCED`
并指出是哪一项变了。CI 上这两条分支都跑（正例必须复现、负例必须被判失败）。

## 结论边界

这个工具能证伪，不能证明。所以范围必须落到具体数字，而不是「覆盖率较高」：

```
接口触达：24 / 215 = 11.2%（核心库 0.10.16+b1a0e846e；30 个用例：bigint 10 / double 10 / string 9 / base64 1）
```

「接口触达」指探针**实际调用到**的接口数。这个百分比是**这几个类型内部**的比例：
核心库另外 900 多个公开函数（数组、迭代器、JSON、格式化工具……）既不在分母里，
也不在覆盖范围内——把它们加进来只会让数字更小，但那个更小的数字说明不了任何新东西。

分母是被测类型（`BigInt` / `String` / `Double` / `Char` / `BytesView` 与四个编码包）
在核心库 `pkg.generated.mbti` 里的**全部**具名方法，由 `scripts/coverage.sh` 现算；
分子来自 `probes/api-touch.txt`，每一条都要过四道校验（接口存在于 `.mbti`、
符号出现在探针源码、用例名存在、符号在该用例自己的函数体里），任何一条不成立
脚本直接退出 1，不给数字。`--check` 会核对上面这一行与本地算出的结果。

**剩下 191 个方法不保证任何东西。** 明确不覆盖的还有：控制流（`OpKind` 里没有跳转原语）、
并发与内存序、内存布局与性能（转录只记值，不记地址与耗时）、panic 的语义与传播
（整数除零在规格里显式定义为 `0`，为的是让差异可观测而不是让进程死掉）、
Float16 与 SIMD、泛型与宏。每一条都指向代码里的一个真实限制，逐条写在 `docs/SCOPE.md`。

**分母会随核心库版本变化**（接口有增删，CI 上是 `24 / 225`），所以那一行把版本写进去了；
`--check` 遇到版本不同会如实说明「分子与用例数一致、分母按本机重算」，
而不是假装数字没变。百分比只在同一版本下可比。

一句话：**它能把「不一致」变成可复现的事实，不能把「一致」变成定理。**
所以本文件说「这 30 个用例逐字节相同」，不说「保证一致」。

## 是否为原创项目

**本项目为原创项目，不是移植项目。**

- 代码全部为本仓库新写，不包含任何第三方源代码的复制或改写；
- 除语言自带的标准库（`moonbitlang/core`）外，没有引入任何第三方包；
  `moon.mod` 里没有任何依赖项，可以逐字核对；
- 设计上参考了业界已有的**方法论**（见下节），但实现、数据模型、收缩算法、
  报告格式、探针与程序格式均为本项目自行设计。

## 关于参考项目的说明

本项目未移植任何具体项目。方法论层面的参考与差异如下：

| 参考对象 | 借鉴的思想 | 本项目的差异 |
| --- | --- | --- |
| Csmith / 编译器差分测试 | 「生成程序 → 多实现比对 → 收缩反例」的总体流程 | 比对对象是**同一编译器的不同后端**，而不是不同编译器；程序为寄存器化直线程序，收缩过程本身不需要重执行（收缩结束后复跑一次确认） |
| wasmtime / wasm-tools 的 differential fuzzing | 用位模式而不是文本比较浮点结果 | 把「位模式」与「宿主格式化」拆成两档可切换的比较维度，并给出字段级归因 |
| C-Reduce / delta debugging | 反例最小化的目标 | 利用直线程序的可判定性，把 O(n log n) 次重执行降为一次反向可达性分析，再用一次复跑证实最小反例仍然重现 |
| Rust `cargo-careful` / Miri | 「同一份代码在另一种执行语义下应当等价」 | 不引入新的执行语义，只比较现有四个后端的真实行为 |
| Hypothesis / QuickCheck 的 shrinking | 结构化收缩优于随机删除 | 收缩保持数据流依赖，保证最小反例仍可读、仍可复现 |

上述项目均未被复制或改写；如后续需要引用其测试语料，将在对应文件中标注来源与许可证。

## 验证方式

**环境**：MoonBit CLI（实测 `moon 0.1.20261020`、`moonc 0.10.16`）、Node.js（`js` 后端）、
C 编译器（`native` 后端：Windows 需 MSVC Build Tools，Linux/macOS 用 gcc）。
某个后端缺工具链时，矩阵会把它标为 `unavailable` 并继续跑其余后端，不会中断。
不需要网络，也不需要任何第三方包。

```bash
moon test && bash scripts/selfcheck.sh                 # 单元测试 + 工具自举
bash scripts/matrix.sh examples/min-div-overflow.json  # 矩阵 → 归因 → 裁定
bash scripts/source-probe.sh                           # 真实库探针，四后端逐字节比对
```

三条命令分别对应三件事：**工具自身可信**（同一份报告在各后端逐字节一致）、
**机制跑得通**（执行 → 矩阵 → 归因 → 裁定一条链）、**真实库用得上**（普通 MoonBit 源码即可接入）。

其余脚本——收缩后复跑 `shrink.sh`、覆盖核对 `coverage.sh --check`、回归基线 `regress.sh`、
常量折叠电池、生成与统计——以及每个脚本断言的具体内容，见 **`docs/TESTING.md`**。
`matrix.sh` 的输出分三段：多后端矩阵（谁和谁不一样）、差异归因（第几步、哪条原语、
哪个字符不同）、规范裁定（依据哪一句）；最后一段是 `docs/FINDINGS.md` 里每条结论的来源。
