## 项目简介

MoonBit 的核心卖点是「一份源码，四个后端」：wasm、wasm-gc、js、native。
但对库作者来说，这个卖点目前是**不可验证的**——`moon test` 在每个后端上都只告诉他
「通过了」或「没通过」，没有任何工具告诉他四个后端**算出来的东西是不是同一个东西**。

同一段代码在四个后端上完全可能给出不同的位模式：NaN 的符号位、
`-2147483648 / -1` 是回绕还是崩溃、`1e21` 打印成 `1e+21` 还是 `1e21`、
代理对字符的长度是 2 还是 1。这类差异不会让测试变红，只会让用户在某一个平台上
拿到错误的结果——而且往往在发布之后才被发现。

MoonDiff 把这件不可见的事变成一张可读的表：用一份规格程序驱动同一批原语在四个后端上执行，
把每一步的结果规范化成**只含 ASCII 的转录**，逐位比对，定位到「第几步、哪个原语、哪种值」不同，
再自动收缩成最小反例。

更进一步，它不止说「不一样」，而是给出**裁定**：依据可引用的语言规范，判定哪一侧违反了语义、
规范值应该是多少、依据是哪一句。裁定分三档——违反规范（缺陷）、实现自由度（不是缺陷）、
无法判定（缺依据就承认判不了）。这个区分是它区别于普通 diff 工具的地方：
把实现自由度报成 bug，会被懂行的人一眼看穿；把真缺陷混进自由度里放过，工具就白做了。

项目本身不引入任何第三方依赖，全部逻辑由 MoonBit 明文实现，
因此**工具自身也能在四个后端上跑出完全相同的报告**——这是它敢去断言别人一致性的前提。

## 项目方向与通用性说明

**方向**：MoonBit 生态中的「可检验性基础设施」（test & verification infrastructure）。

**通用性**体现在三个层面：

1. **与被测库无关**。MoonDiff 不针对某个具体库，它针对的是 MoonBit 的**原语语义**：
   整数除法与取模、位宽边界、浮点运算与格式化、字符串码元/码点、数组与转换。
   任何库最终都建立在这些原语之上，因此任何库作者都能用它定位「我的包在哪个后端上行为不同」。
2. **与后端数量无关**。矩阵不是写死的四列，而是运行时探测：本机缺 C 编译器时
   `native` 自动标记为 `unavailable` 并跳过，装上之后自动进入矩阵。
   仓库自带的 CI 在 Linux runner 上跑满 **wasm / wasm-gc / js / native 四个后端**
   （Linux 上 native 只需 gcc），因此「四后端」不是一句声明，而是每次提交都被验证的事实。
3. **与运行环境无关**。程序用 JSON 描述、转录是纯 ASCII、报告只依赖 argv 与 stdout，
   因此它可以在 CI、在容器、在没有图形界面的机器上被脚本直接调用。

## 预期使用场景

### 场景一：库作者发布前自查

一位作者写了一个数值/编解码/文本处理库，`moon test` 全绿。
他在发布前跑一次 `scripts/matrix.sh`：

- 四个后端 PASS → 可以放心发版，README 里可以写「已验证四后端一致」；
- 出现 DIVERGENT → 报告直接给出步号与原语名，他只需看那一条指令就能定位；
- 出现 ABORT → 某个后端在途中崩溃，用 `scripts/localize.py` 二分出确切步号。

这条流程把「我觉得应该一致」变成「我验证过一致」。

### 场景二：核心库/编译器改动后的回归

MoonBit 工具链与核心库迭代很快，一次优化（常量折叠、内联、指令选择）就可能
在某个后端上改变一个边界值的行为。把 MoonDiff 挂进 CI：

```
scripts/matrix.sh examples/probe-*.json
```

探针是固定的、可复现的，任何一次语义漂移都会让对应行从 PASS 变成 FAIL，
而且报告里直接写明是哪一种值、哪一位不同。

### 场景三：教学与规范讨论

「`-2147483648 / -1` 到底应该是什么结果？」这个问题在讨论区很难用文字说清。
MoonDiff 直接给出结论，而不是把差异摆出来让人自己查规范：

```
+--------------+----------+--------+------------------------------------+
| backend      | status   | step   | note                               |
+--------------+----------+--------+------------------------------------+
| wasm         | ABORT    | ?      | 无结束哨兵：trap/abort，转录可能被丢弃 |
| wasm-gc      | ABORT    | ?      | 无结束哨兵：trap/abort，转录可能被丢弃 |
| js           | PASS     | -      | baseline                           |
+--------------+----------+--------+------------------------------------+

裁定
  结论   : 违反语言规范（Verdict: SPEC-VIOLATION）
  违规方 : wasm, wasm-gc
  规范值 : i-2147483648
  依据   : moonbitlang/core 文档：Int 为 32 位整数，采用二补数运算，
           溢出按回绕处理（示例 2147483647 + 1 == -2147483648）。
           同一规则下 INT_MIN / -1 的规范结果应为 INT_MIN 本身，而非终止进程。
```

注意 `step` 显示 `?` 而不是 `0`：trap 会连已打印的转录一起丢弃，步号不可信，
此时精确步号由 `scripts/localize.py` 前缀二分给出。任何人都能用仓库里的
`examples/min-div-overflow.json` 在三条指令内复现整条证据链。

### 场景四：包生态的横向体检

把若干已发布包的公开 API 转写成规格程序（同一份 JSON 喂给四个后端），
可以批量得到一张「生态一致性体检表」，找出哪些包在哪个后端上有隐患。
这是 MoonDiff 作为**基础设施**而非单点工具的长期价值。

## 拟实现的核心功能

- **规格程序模型**：寄存器化直线程序，覆盖 54 条原语
  （32 位整数、64 位整数、双精度浮点、六种转换、字符串、数组），
  每条指令对应一个明确的核心库操作。
- **JSON 编解码**：程序序列化为单行紧凑 JSON；64 位整数用十进制字符串、
  浮点用 16 位十六进制位串承载，保证编解码过程不丢失任何一位。
- **参照解释器（spec runtime）**：把规格程序执行成转录；解释器自身不做算术，
  只把每条指令转发给宿主原语，因此差异必然来自后端而不是来自工具。
- **规范值编码**：值被渲染成纯 ASCII 的规范形式（整数用补码、浮点用品模式、
  字符串带码元数/码点数），保证任何终端、任何编码环境下都能逐字节比对。
- **三种比较档位**：`bit-exact`（只看位模式）、`strict`（位模式 + 宿主格式化）、
  `semantic`（折叠 NaN 载荷与 ±0），用于在「漏报」与「噪声」之间取舍。
- **差异定位**：首处分歧的步号、原语名、两侧原文、第一个不同字符的位置，
  并归类为「位模式不一致 / 格式化不一致 / 形态不一致」。
- **多后端矩阵**：一列一个后端的一致性表，自动识别少数派，并单独识别
  「终止性差异」（trap：转录里缺少结束哨兵）。
- **确定性生成器**：xorshift64* 伪随机源，同一种子在任何后端都给出同一序列；
  常量池刻意包含 ±0、±inf、NaN、次正规数、整数上下界、代理对字符。
- **覆盖引导语料库**：以原语 + 分支为边，只保留带来新边的输入，避免语料爆炸。
- **结构化收缩**：基于反向依赖闭包，把几百条指令压到 3–5 条，
  且**不需要重新执行后端**（直线程序的删除是可判定的语义空操作）。
- **手工探针电池**：8 组固定探针（浮点取余、除零、NaN 运算、转换越界、
  64 位溢出、32 位溢出、Unicode、次正规数），永远可复现。
- **常量折叠电池**：24 条源码级常量表达式，专抓「只在编译期折叠才出现」的差异。
- **编排脚本**：`scripts/matrix.sh` / `matrix.ps1` 自动探测可用后端、
  并行执行、汇总成矩阵；`scripts/localize.py` 二分定位崩溃点。
- **规范裁定（对「谁错了」给出结论）**：报告不止说「两边不一样」，而是依据可引用的
  语言规范判定哪一侧违反了语义——违规方、规范值、依据逐条给出。裁定分三档：
  `SPEC-VIOLATION`（违反规范，是缺陷）、`IMPLEMENTATION-FREEDOM`（规范未规定，
  属实现自由度，不算缺陷）、`UNDETERMINED`（缺依据，明确承认判不了）。
  三档分开的理由很直接：把实现自由度误报成缺陷，会被懂行的人一眼看穿；
  把真缺陷混进「自由度」里放过，工具就失去了意义。
- **规格化冻结的期望值**：`tests/expected.txt` 是回归基线，已知差异与已知的
  实现自由度都记在里面，CI 只对**新增**差异报警——既不反复刷屏，也不静默放过。
- **自举自检**：`scripts/selfcheck.sh` 把工具自己送进矩阵，验证 `stats` / `matrix` /
  `shrink` / `gen` 在四个后端上输出逐字节一致。
- **测试与文档**：31 个单元测试覆盖编码、编解码往返、解释器确定性、随机源确定性、
  依赖闭包、规范裁定边界；`docs/` 下含架构、发现、测试方法、原创性排查记录。

## 是否为原创项目

**本项目为原创项目，不是移植项目。**

- 代码全部为本仓库新写，不包含任何第三方源代码的复制或改写；
- 唯一的外部依赖是 MoonBit 标准库（`moonbitlang/core`），未引入任何第三方包；
- 设计上参考了业界已有的**方法论**（见下节），但实现、数据模型、收缩算法、
  报告格式、探针与程序格式均为本项目自行设计。

## 关于参考项目的说明

本项目未移植任何具体项目。方法论层面的参考与差异如下：

| 参考对象 | 借鉴的思想 | 本项目的差异 |
| --- | --- | --- |
| Csmith / 编译器差分测试 | 「生成程序 → 多实现比对 → 收缩反例」的总体流程 | MoonDiff 的比对对象是**同一编译器的不同后端**，而不是不同编译器；程序模型为寄存器化直线程序，可做无重执行的收缩 |
| wasmtime / wasm-tools 的 differential fuzzing | 用位模式而不是文本比较浮点结果 | 本项目把「位模式」与「宿主格式化」拆成两档可切换的比较维度，并给出字段级归因 |
| C-Reduce / delta debugging | 反例最小化的目标 | 本项目利用直线程序的可判定性，把 O(n log n) 次重执行降为一次反向可达性分析 |
| Rust `cargo-careful` / Miri | 「同一份代码在另一种执行语义下应当等价」 | 本项目不引入新的执行语义，只比较现有四个后端的真实行为 |
| Hypothesis / QuickCheck 的 shrinking | 结构化收缩优于随机删除 | 收缩保持数据流依赖，保证最小反例仍可读、仍可复现 |

上述项目均未被复制或改写；如后续需要引用其测试语料，将在对应文件中标注来源与许可证。

## 验证方式

以下三条命令按顺序执行，即可复现本项目的全部主张。全部命令均为实测可跑，
不需要任何第三方依赖或网络访问。

```bash
# 1. 单元测试 + 工具自举（工具自己在各后端上必须给出同一份报告）
moon test
bash scripts/selfcheck.sh

# 2. 一条命令走完「执行 → 矩阵 → 收缩 → 裁定」的完整证据链
bash scripts/matrix.sh probe:int-overflow          # 违反规范：wasm/wasm-gc 终止，js 回绕
bash scripts/matrix.sh examples/min-div-overflow.json   # 同一缺陷的 3 条指令最小复现

# 3. 回归基线：已知差异在册，只对新增差异报警
bash scripts/regress.sh
```

`scripts/matrix.sh` 的输出包含三段：多后端矩阵（谁和谁不一样）、差异归因
（第几步、哪条原语、哪个字符不同）、规范裁定（谁错了、规范值是什么、依据哪一句）。
最后一段是 `docs/FINDINGS.md` 里每条结论的来源。

其他可单独调用的能力：

```bash
# 常量折叠电池（24 条编译期表达式，跨后端比对）
for t in wasm wasm-gc js; do moon run cmd/driver --target $t -- literals; done

# 生成 → 统计 → 收缩
PROG=$(moon run cmd/moondiff --target wasm -- gen 7 120 strict 8 | tail -1)
moon run cmd/moondiff --target wasm -- stats "$PROG"
moon run cmd/moondiff --target wasm -- shrink "$PROG" 26

# 终止性差异（trap）的精确步号：前缀二分
python scripts/localize.py examples/min-div-overflow.json
```

## 已观测到的真实差异与裁定

仓库 `docs/FINDINGS.md` 记录了在本机复现的跨后端差异，均附最小复现与规范依据。
两条的性质**不同**，因此裁定不同——这个区分本身就是工具的产出：

### 一、违反语言规范：`-2147483648 / -1`

```
wasm / wasm-gc -> 进程终止（divide result unrepresentable）
js             -> -2147483648（回绕）
```

**裁定：`SPEC-VIOLATION`，违规方是 wasm 与 wasm-gc。**

依据是 MoonBit 核心库文档对 `Int` 的规定：32 位整数、二补数运算、溢出按回绕处理
（文档示例即 `2147483647 + 1 == -2147483648`）。同一规则下 `INT_MIN / -1` 的规范结果
应当是 `INT_MIN` 本身，终止进程属于后端实现未对齐语言语义。

这条差异不会让 `moon test` 变红，只会让 wasm 平台上这个边界输入的使用者拿到
一个进程崩溃——比拿到错值更难排查。最小复现只有 3 条指令，
见 `examples/min-div-overflow.json`。

### 二、实现自由度：常量折叠后 NaN 的符号位

```
(0.0 / 0.0).reinterpret_as_int64()
wasm / wasm-gc -> 0xFFF8000000000000（负 quiet NaN）
js             -> 0x7FF8000000000000（正 quiet NaN）
```

**裁定：`IMPLEMENTATION-FREEDOM`，不构成缺陷。**

IEEE 754-2019 §6.2.3 不规定 NaN 的符号位，正负 quiet NaN 都是合法结果。
因此「各后端不同」本身不是 bug。它值得记录的真实理由是工程性的：
同一表达式在不同编译路径（常量折叠 vs 运行期）给出不同位模式，会让依赖位序列化的
代码——哈希、缓存键、黄金文件比对——出现平台相关行为，应当显式归一化。

把这一条误报成 bug 是差分工具最常见的过度断言；本项目把它单列为自由度，
并在 `semantic` 比较档里折叠掉。

### 两条结论的共同点

它们都不影响「测试是否通过」，只影响「结果是否正确」。这正是本项目要解决的问题：
`moon test` 回答「有没有通过」，MoonDiff 回答「四个后端算的是不是同一个东西」。
