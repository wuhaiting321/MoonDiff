## 项目简介

MoonBit 的核心卖点是「一份源码，四个后端」：wasm、wasm-gc、js、native。
但对库作者来说，这个卖点目前是**不可验证的**——`moon test` 在每个后端上都只告诉他
「通过了」或「没通过」，没有任何工具告诉他四个后端**算出来的东西是不是同一个东西**。

同一段代码在四个后端上完全可能给出不同的位模式：NaN 的符号位、
`-2147483648 / -1` 是回绕还是崩溃、`1e21` 打印成 `1e+21` 还是 `1e21`、
代理对字符的长度是 2 还是 1。这类差异不会让测试变红，只会让用户在某一个平台上
拿到错误的结果——而且往往在发布之后才被发现。

MoonDiff 把这件不可见的事变成一张可读的表：用一份规格程序驱动同一批原语在四个后端上执行，
把每一步的结果规范化成**只含 ASCII 的转录**，逐位比对，定位到「第几步、哪个原语、哪种值」不同，
再自动收缩成最小反例。

更进一步，它不止说「不一样」，而是给出**裁定**：有条款就引出条款，没条款就只报差异、
指出规范缺哪一句。裁定分四档——违反规范（有条款支撑，是缺陷）、实现自由度（条款写明由实现自选）、
无条款不一致（查过条款，没规定）、无法判定（缺依据就承认判不了）。
这个区分是它区别于普通 diff 工具的地方：把实现自由度报成 bug，会被懂行的人一眼看穿；
把「规范没写」硬说成「违反规范」，会被追问出处；把真缺陷混进自由度里放过，工具就白做了。

项目本身不引入任何第三方依赖，全部逻辑由 MoonBit 明文实现，
因此**工具自身也能在四个后端上跑出完全相同的报告**——这是它敢去断言别人一致性的前提。

## 项目方向与通用性说明

**方向**：MoonBit 生态中的「可检验性基础设施」（test & verification infrastructure）。

**通用性**体现在三个层面：

1. **与被测库无关**。MoonDiff 不针对某个具体库，它针对的是 MoonBit 的**原语语义**：
   整数除法与取模、位宽边界、浮点运算与格式化、字符串码元/码点、数组与转换。
   任何库最终都建立在这些原语之上，因此任何库作者都能用它定位「我的包在哪个后端上行为不同」。
2. **与后端数量无关**。矩阵不是写死的四列，而是运行时探测：本机缺 C 编译器时
   `native` 自动标记为 `unavailable` 并跳过，装上之后自动进入矩阵。
   仓库自带的 CI 在 Linux runner 上跑满 **wasm / wasm-gc / js / native 四个后端**
   （Linux 上 native 只需 gcc），因此「四后端」不是一句声明，而是每次提交都被验证的事实。
3. **与运行环境无关**。程序用 JSON 描述、转录是纯 ASCII、报告只依赖 argv 与 stdout，
   因此它可以在 CI、在容器、在没有图形界面的机器上被脚本直接调用。

## 预期使用场景

### 场景一：库作者发布前自查

一位作者写了一个数值/编解码/文本处理库，`moon test` 全绿。
他在发布前跑一次 `scripts/matrix.sh`：

- 四个后端 PASS → 可以放心发版，README 里可以写「已验证四后端一致」；
- 出现 DIVERGENT → 报告直接给出步号与原语名，他只需看那一条指令就能定位；
- 出现 ABORT → 某个后端在途中崩溃，用 `scripts/localize.py` 二分出确切步号。

这条流程把「我觉得应该一致」变成「我验证过一致」。

### 场景二：核心库/编译器改动后的回归

MoonBit 工具链与核心库迭代很快，一次优化（常量折叠、内联、指令选择）就可能
在某个后端上改变一个边界值的行为。把 MoonDiff 挂进 CI：

```
scripts/matrix.sh examples/probe-*.json
```

探针是固定的、可复现的，任何一次语义漂移都会让对应行从 PASS 变成 FAIL，
而且报告里直接写明是哪一种值、哪一位不同。

### 场景三：教学与规范讨论

「`-2147483648 / -1` 到底应该是什么结果？」这个问题在讨论区很难用文字说清。
MoonDiff 给出的是三样东西——差在哪、有没有条款管、条款原文是什么——而不是替规范下判断：

```
+--------------+----------+--------+------------------------------------+
| backend      | status   | step   | note                               |
+--------------+----------+--------+------------------------------------+
| wasm         | ABORT    | ?      | 无结束哨兵：trap/abort，转录可能被丢弃 |
| wasm-gc      | ABORT    | ?      | 无结束哨兵：trap/abort，转录可能被丢弃 |
| js           | PASS     | -      | baseline                           |
+--------------+----------+--------+------------------------------------+

裁定
  结论   : 无条款不一致（Verdict: UNSPECIFIED-DIVERGENCE）
  议题   : 整数除法/取模的商（余数）不可表示：min_value / -1
  分歧   : wasm=ABORT, wasm-gc=ABORT, js=i-2147483648
  缺口   : 该条目全文只规定「除数为 0 时 panic」，未规定商不可表示
           （min_value / -1）时应回绕还是终止。回绕一侧与四条算术运算的
           定宽二补数语义一致，终止一侧与硬件除法异常一致，两者都能自圆其说；
           本工具只报事实，不替规范下判断。
  依据   : builtin/intrinsics.mbt:298-309
  原文   : "Throws a panic if `divisor` is zero."
```

注意 `step` 显示 `?` 而不是 `0`：trap 会连已打印的转录一起丢弃，步号不可信，
此时精确步号由 `scripts/localize.py` 前缀二分给出。任何人都能用仓库里的
`examples/min-div-overflow.json` 在三条指令内复现整条证据链。

### 场景四：包生态的横向体检

把若干已发布包的公开 API 转写成规格程序（同一份 JSON 喂给四个后端），
可以批量得到一张「生态一致性体检表」，找出哪些包在哪个后端上有隐患。
这是 MoonDiff 作为**基础设施**而非单点工具的长期价值。

## 拟实现的核心功能

- **源码探针（零 DSL 接入）**：探针就是普通 MoonBit 源码，直接 `import` 真实包、调用真实函数、
  打印规范形式结果；工具在多后端执行同一份源码并逐字节比对 stdout。`probes/moon.pkg` 不依赖
  本项目任何包，因此「不写指令语言也能用」是可验证的。首批 30 个探针覆盖 `BigInt`、`Double`、
  `String` 与 UTF-8 / ASCII / Base64 编码，状态分 `PASS` / `DIVERGENT` / `ABORT` / `unavailable`。
- **规格程序模型**：寄存器化直线程序，覆盖 54 条原语
  （32 位整数、64 位整数、双精度浮点、六种转换、字符串、数组），
  每条指令对应一个明确的核心库操作。
- **JSON 编解码**：程序序列化为单行紧凑 JSON；64 位整数用十进制字符串、
  浮点用 16 位十六进制位串承载，保证编解码过程不丢失任何一位。
- **参照解释器（spec runtime）**：把规格程序执行成转录；解释器自身不做算术，
  只把每条指令转发给宿主原语，因此差异必然来自后端而不是来自工具。
- **规范值编码**：值被渲染成纯 ASCII 的规范形式（整数用补码、浮点用品模式、
  字符串带码元数/码点数），保证任何终端、任何编码环境下都能逐字节比对。
- **三种比较档位**：`bit-exact`（只看位模式）、`strict`（位模式 + 宿主格式化）、
  `semantic`（折叠 NaN 载荷与 ±0），用于在「漏报」与「噪声」之间取舍。
- **差异定位**：首处分歧的步号、原语名、两侧原文、第一个不同字符的位置，
  并归类为「位模式不一致 / 格式化不一致 / 形态不一致」。
- **多后端矩阵**：一列一个后端的一致性表，自动识别少数派，并单独识别
  「终止性差异」（trap：转录里缺少结束哨兵）。
- **确定性生成器**：xorshift64* 伪随机源，同一种子在任何后端都给出同一序列；
  常量池刻意包含 ±0、±inf、NaN、次正规数、整数上下界、代理对字符。
- **覆盖引导语料库**：以原语 + 分支为边，只保留带来新边的输入，避免语料爆炸。
- **结构化收缩**：基于反向依赖闭包，把几百条指令压到 3–5 条。删除是否安全
  可以静态判定（直线程序的删除是语义空操作），但工具不拿这个论证当结论——
  收缩之后会**把更小的程序再交给同一批后端跑一遍**，比对后端集合、终止集合、
  分歧原语与两侧取值，输出 `verified: reproduce` 或 `NOT-REPRODUCED` 及具体原因。
- **手工探针电池**：8 组固定探针（浮点取余、除零、NaN 运算、转换越界、
  64 位溢出、32 位溢出、Unicode、次正规数），永远可复现。
- **常量折叠电池**：24 条源码级常量表达式，专抓「只在编译期折叠才出现」的差异。
- **编排脚本**：`scripts/matrix.sh` / `matrix.ps1` 自动探测可用后端、
  并行执行、汇总成矩阵；`scripts/shrink.sh` 收缩并复跑验证；
  `scripts/localize.py` 二分定位崩溃点。
- **规范裁定（对「谁错了」给出结论，且只在有出处时下结论）**：报告不止说「两边不一样」，
  而是四档分开：`SPEC-VIOLATION`（有条款要求某个值，某后端给了别的值）、
  `IMPLEMENTATION-FREEDOM`（条款明文把选择权留给实现）、
  `UNSPECIFIED-DIVERGENCE`（查过最接近的条款、其中没有规定）、
  `UNDETERMINED`（没匹配到规则或缺操作数，明确承认判不了）。
  出处不是说明文字，而是类型的一部分：`Source` 只能由校验过非空的构造函数生成，
  且是 `Violation` 的必填参数——**没有条款原文的违规裁定在编译期就写不出来**。
  四档分开的理由很直接：把实现自由度误报成缺陷，会被懂行的人一眼看穿；
  把「规范没写」硬说成「违反规范」，会被追问出处；把真缺陷混进「自由度」里放过，
  工具就失去了意义。
- **规格化冻结的期望值**：`tests/expected.txt` 是回归基线，已知差异与已知的
  实现自由度都记在里面，CI 只对**新增**差异报警——既不反复刷屏，也不静默放过。
- **自举自检**：`scripts/selfcheck.sh` 把工具自己送进矩阵，验证 `stats` / `matrix` /
  `shrink` / `gen` 在四个后端上输出逐字节一致。
- **测试与文档**：50 个单元测试覆盖编码、编解码往返、解释器确定性、随机源确定性、
  依赖闭包、四档裁定的边界、收缩复跑的五项比较；`docs/` 下含架构、发现、
  测试方法、覆盖边界、原创性排查记录。

## 是否为原创项目

**本项目为原创项目，不是移植项目。**

- 代码全部为本仓库新写，不包含任何第三方源代码的复制或改写；
- 唯一的外部依赖是 MoonBit 标准库（`moonbitlang/core`），未引入任何第三方包；
- 设计上参考了业界已有的**方法论**（见下节），但实现、数据模型、收缩算法、
  报告格式、探针与程序格式均为本项目自行设计。

## 关于参考项目的说明

本项目未移植任何具体项目。方法论层面的参考与差异如下：

| 参考对象 | 借鉴的思想 | 本项目的差异 |
| --- | --- | --- |
| Csmith / 编译器差分测试 | 「生成程序 → 多实现比对 → 收缩反例」的总体流程 | MoonDiff 的比对对象是**同一编译器的不同后端**，而不是不同编译器；程序模型为寄存器化直线程序，可做无重执行的收缩 |
| wasmtime / wasm-tools 的 differential fuzzing | 用位模式而不是文本比较浮点结果 | 本项目把「位模式」与「宿主格式化」拆成两档可切换的比较维度，并给出字段级归因 |
| C-Reduce / delta debugging | 反例最小化的目标 | 本项目利用直线程序的可判定性，把 O(n log n) 次重执行降为一次反向可达性分析 |
| Rust `cargo-careful` / Miri | 「同一份代码在另一种执行语义下应当等价」 | 本项目不引入新的执行语义，只比较现有四个后端的真实行为 |
| Hypothesis / QuickCheck 的 shrinking | 结构化收缩优于随机删除 | 收缩保持数据流依赖，保证最小反例仍可读、仍可复现 |

上述项目均未被复制或改写；如后续需要引用其测试语料，将在对应文件中标注来源与许可证。

## 验证方式

**环境**：MoonBit CLI（实测 `moon 0.1.20261020`、`moonc 0.10.16`）、Node.js（`js` 后端）、
C 编译器（`native` 后端：Windows 需 MSVC Build Tools，Linux/macOS 用 gcc）。
某个后端缺工具链时，矩阵会把它标为 `unavailable` 并继续跑其余后端，不会中断；
`python` 仅在 `scripts/localize.py` 中用到，属可选项。

以下命令按顺序执行即可复现本项目的全部主张；除上述工具链外不需要任何第三方包，
也不需要网络访问。

```bash
# 1. 单元测试 + 工具自举（工具自己在各后端上必须给出同一份报告）
moon test
bash scripts/selfcheck.sh

# 2. 一条命令走完「执行 → 矩阵 → 收缩 → 裁定」的完整证据链
bash scripts/matrix.sh probe:int-overflow          # 违反规范：wasm/wasm-gc 终止，js 回绕
bash scripts/matrix.sh examples/min-div-overflow.json   # 同一缺陷的 3 条指令最小复现

# 3. 回归基线：已知差异在册，只对新增差异报警
bash scripts/regress.sh

# 4. 源码探针：普通 MoonBit 直接调用真实包，四后端逐字节比对
bash scripts/source-probe.sh

# 5. 收缩后复跑：最小反例必须真的还能复现同一个分歧
bash scripts/shrink.sh examples/min-div-overflow.json

# 6. 覆盖边界：接口触达率现算，并与 README 里的数字逐字核对
bash scripts/coverage.sh --check
```

`scripts/matrix.sh` 的输出包含三段：多后端矩阵（谁和谁不一样）、差异归因
（第几步、哪条原语、哪个字符不同）、规范裁定（谁错了、规范值是什么、依据哪一句）。
最后一段是 `docs/FINDINGS.md` 里每条结论的来源。

其他可单独调用的能力：

```bash
# 常量折叠电池（24 条编译期表达式，跨后端比对）
for t in wasm wasm-gc js; do moon run cmd/driver --target $t -- literals; done

# 生成 → 统计 → 收缩
PROG=$(moon run cmd/moondiff --target wasm -- gen 7 120 strict 8 | tail -1)
moon run cmd/moondiff --target wasm -- stats "$PROG"
moon run cmd/moondiff --target wasm -- shrink "$PROG" 26

# 终止性差异（trap）的精确步号：前缀二分
python scripts/localize.py examples/min-div-overflow.json
```

## 源码探针：不写 DSL 也能用

规格程序不是唯一入口。`probes/` 是一组**普通的 MoonBit 源码**：直接 `import` 真实包、
调用真实函数、`println` 结果，工具只负责在多个后端执行并逐字节比对 stdout。

```moonbit
fn case_bigint_mul() -> Unit {
  let a = @bigint.BigInt::from_string("123456789012345678901234567890")
  let b = @bigint.BigInt::from_string("-987654321098765432109876543210")
  emit("bigint-mul", (a * b).to_string())
}
```

`probes/moon.pkg` 里 **没有** `wuhaiting321/moondiff`——探针不依赖本项目的任何代码。
这条是硬约束，也是「它对你真的可用」的唯一证据。

一条命令得到矩阵（下面节选 3 行，完整 30 行由脚本输出）：

```
+----------------------------+-----------+-----------+-----------+-----------+
| case                       | wasm      | wasm-gc   | js        | native    |
+----------------------------+-----------+-----------+-----------+-----------+
| bigint-mul                 | PASS      | PASS      | PASS      | PASS      |
| double-nan-literal         | PASS      | PASS      | DIVERGENT | PASS      |
| string-length              | PASS      | PASS      | PASS      | PASS      |
+----------------------------+-----------+-----------+-----------+-----------+
```

状态只有四种：`PASS`（逐字节一致）、`DIVERGENT`（存在差异）、`ABORT`（某后端在途中终止）、
`unavailable`（该后端缺工具链，**不冒充 PASS**）。

**接入你自己的包，三步**：

1. 在 `probes/moon.pkg` 的 `import` 里加上你的包；
2. 在 `probes/main.mbt` 的 `match` 里加一个分支，调用你的函数并用 `emit` 打印；
3. 跑 `bash scripts/source-probe.sh --update` 记录基线，之后 `--check` 只对新增差异报警。

源码探针与 `moon test` 的分工要说清：`moon test` 在**每个后端上独立判断通过与否**，
从不比较后端之间；源码探针比的是**同一份输出在多个后端上是否逐字节相同**。
两者不是替代关系——测试通过但输出不同，正是本工具要暴露的那一类问题。

源码探针只报「不一致」，不做裁定；`SPEC-VIOLATION` / `UNSPECIFIED-DIVERGENCE` /
`IMPLEMENTATION-FREEDOM` 这些判定由规格程序模式给出。已知的 `DIVERGENT` 在
`tests/source-expected.txt` 里入册，裁定见 `docs/FINDINGS.md`。

### 覆盖边界与接口触达

这个工具能证伪，不能证明。所以覆盖范围必须写死到具体数字，而不是「覆盖率较高」：

```
接口触达：24 / 215 = 11.2%（核心库 0.10.16+b1a0e846e；30 个用例：bigint 10 / double 10 / string 9 / base64 1）
```

分母是被测类型（`BigInt` / `String` / `Double` / `Char` / `BytesView` 与四个编码包）
在核心库 `pkg.generated.mbti` 里的**全部**具名方法，由 `bash scripts/coverage.sh`
从 `.mbti` 现算；分子来自 `probes/api-touch.txt`，每一条都要过四道校验
（接口存在于 `.mbti`、符号出现在探针源码、用例名存在、符号在该用例自己的函数体里），
任何一条不成立脚本直接退出 1，不给数字。`bash scripts/coverage.sh --check`
会核对上面这一行与本地算出来的是否逐字一致。

**分母是核心库版本的函数**：接口会随版本增删，所以那一行把版本写进去了。
换核心库版本后跑 `--check`，它会说清「分子与用例数一致、分母按本机重算」，
而不是假装数字没变——百分比只在同一版本下可比。

剩下 191 个未被触达的方法，**不保证任何东西**。为什么不把数字做大、为什么不覆盖
控制流、并发、内存布局、Float16、泛型，逐条写在 `docs/SCOPE.md` 里，
每条都指向代码里的一个真实限制。

## 已观测到的真实差异与裁定

仓库 `docs/FINDINGS.md` 记录了在本机复现的跨后端差异，均附最小复现与规范依据。
两条的性质**不同**，因此裁定不同——这个区分本身就是工具的产出。
编号是发现顺序、不是严重程度，下面按严重程度排列；可粘贴的上游 issue 正文见
`docs/UPSTREAM_ISSUE.md`。

### 一、无条款不一致：`-2147483648 / -1`（发现 2）

```
wasm / wasm-gc -> 进程终止（divide result unrepresentable）
js             -> -2147483648（回绕）
```

（native 列本机缺 MSVC 未实测，不写入结论；CI 上的四后端作业会给出它。）

**裁定：`UNSPECIFIED-DIVERGENCE`——只报不一致，不指认违规方。**

上一版这一条判的是 `SPEC-VIOLATION`，理由是「`Int` 是定宽二补数、溢出回绕，
所以除法也该回绕」。这一版收回这一步，因为复核文档后边界很清楚：
`Add` / `Sub` / `Mul` 三条**明文**写回绕，而 `Div for Int32`（`builtin/intrinsics.mbt:298-309`）
全文只规定「除数为 0 时 panic」，对「商不可表示」一个字没有。
从「加法的文档写了回绕」推到「除法也该回绕」，是推断，不是引用；
拿推断去指控后端，就是「缺少适用条款支撑」。

仍然照报，因为两件事实都确证：四份输出不同（可复现），规范缺这一条（可核对）。
回绕一侧与四条算术运算的二补数语义一致，终止一侧与硬件除法异常一致，
两者都能自圆其说——**这正是需要上游补一条规定的地方，而不是本工具替它选一边**。
上游 issue 的诉求也相应从「请修 bug」变成「请补规定或确认设计」，见 `docs/UPSTREAM_ISSUE.md`。

最小复现只有 3 条指令，见 `examples/min-div-overflow.json`；
`/` 与 `%` 两个运算符都覆盖到。

### 二、实现自由度：常量折叠后 NaN 的符号位（发现 1）

```
(0.0 / 0.0).reinterpret_as_int64()
wasm / wasm-gc -> 0xFFF8000000000000（负 quiet NaN）
js             -> 0x7FF8000000000000（正 quiet NaN）
```

**裁定：`IMPLEMENTATION-FREEDOM`，不构成缺陷。**

IEEE 754-2019 §6.2.3 不规定 NaN 的符号位，正负 quiet NaN 都是合法结果。
因此「各后端不同」本身不是 bug。它值得记录的真实理由是工程性的：
同一表达式在不同编译路径（常量折叠 vs 运行期）给出不同位模式，会让依赖位序列化的
代码——哈希、缓存键、黄金文件比对——出现平台相关行为，应当显式归一化。

把这一条误报成 bug 是差分工具最常见的过度断言；本项目把它单列为自由度，
并在 `semantic` 比较档里折叠掉。

### 两条结论的共同点

它们都不影响「测试是否通过」，只影响「结果是否正确」。这正是本项目要解决的问题：
`moon test` 回答「有没有通过」，MoonDiff 回答「四个后端算的是不是同一个东西」。
