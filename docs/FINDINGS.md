# 已观测到的跨后端差异

记录时间：2026-11-12（裁定机制与结论更新于 2026-11-13、2026-11-18）
工具链：`moon 0.1.20261020 (2284bd2 2026-10-20)`，核心库 `moonbitlang/core 0.10.16`
本机可用后端：`wasm` / `wasm-gc` / `js`（本机未装 MSVC Build Tools，`native` 由 CI 覆盖）

> 本文的每条结论都可以用仓库内的命令复现，并已写入回归基线 `tests/expected.txt`。
> 文中判定只针对上述工具链版本；工具链升级后若行为改变，基线会立刻报警。

## 判定分四档，不能混为一谈

差分工具在两个方向上都会犯错：把「不一样」直接说成 bug（过度断言），
或者只说「不一样」不给判断（等于没做裁定）。四档把两头都堵住：

| 标签 | 含义 | 处置 |
| --- | --- | --- |
| `SPEC-VIOLATION:<议题>` | 有条款要求某个值，某后端给了别的值 | 缺陷，上报并修 |
| `IMPLEMENTATION-FREEDOM:<议题>` | 条款明文把选择权留给实现 | 不是缺陷，工程上归一化 |
| `UNSPECIFIED-DIVERGENCE:<议题>` | 查过最接近的条款，其中没有规定 | 报不一致 + 指出缺口，推动上游补规定 |
| `UNDETERMINED` | 没匹配到规则，或操作数不是常量 | 明确承认判不了，不猜 |

出处是类型的一部分，不是说明文字：`Source`（文档 / 定位 / 原文）字段私有，
只能由拒绝空值的构造函数生成，并且是 `Violation` 的必填参数。
**想写一条「违规」却拿不出原文，编译就过不去**——这条约束由
「`Source` 拒绝空白项」的负例单测守着。

这个分级是 `src/oracle` 的实现对象，也是它能被称为「裁定」而不只是「比对」的原因。

> 编号 1、2 是**发现顺序**，不是严重程度；本节按严重程度排列，所以发现 2 在前。

## 发现 2：`INT_MIN / -1` —— 无条款不一致

**裁定：`UNSPECIFIED-DIVERGENCE`。只报不一致，不指认违规方。**

### 现象

```
-2147483648 / -1
  wasm / wasm-gc -> RuntimeError: divide result unrepresentable（进程终止）
  js             -> -2147483648（回绕）
```

### 为什么不是「违反规范」

2026-11-18 复核文档后把这一条从 `SPEC-VIOLATION` 降为 `UNSPECIFIED-DIVERGENCE`。

原来的依据是「`Int` 是定宽二补数、溢出回绕，所以除法溢出也该回绕」。这是**推断**，
不是**引用**。原文的实际边界是：

- `Add for Int32`（`builtin/intrinsics.mbt:234-246`）、`Sub`（249-251）、`Mul`（282-283）
  三条**明文**写「溢出按二补数回绕」；
- `Div for Int32`（298-309）全文只写「除数为 0 时 panic」，对「商不可表示」一个字没有；
- `Mod for Int32`（322-344）写的是「除数为 0 时行为未定义」，同样没有覆盖 `min % -1`。

从「加法的文档写了回绕」推到「除法也该回绕」，中间那一步没有出处。
拿推断去指控后端，就是「缺少适用条款支撑」——评审指出的正是这一点。
所以这一版把断言收回到能举证的位置：

1. 四份输出确实不同（可复现，见下方最小复现）；
2. 规范确实没写这一条（可核对，行号在上一段）。

两条都能查，结论就不再依赖解释。

### 为什么仍然值得上报

回绕一侧与四条算术运算的定宽二补数语义一致；终止一侧与 x86 / ARM 的除法异常一致。
**两者都能自圆其说**，所以这不是「谁错」，而是「规范缺一格」。
需要上游决定的是「要不要把这一格补上」，不是「哪个后端该改」。

上游 issue 的诉求因此从「请修 bug」改为「请补规定或确认设计」，
正文见 `docs/UPSTREAM_ISSUE.md`。

### 排除项

除数为 0 的情形不在此列：本项目在规格里把整数除零显式定义为 0，
不会被这一条覆盖；`divisor == 0` 时 `Div` 条目要求 panic，属于另一件事。

### 为什么这条比「取到错值」更严重

这是**终止性差异**，不是取值差异：wasm 侧进程直接死掉，连已经打印的转录都被丢弃。
调用方拿到的是崩溃，不是错误值；在没有调试器的环境里，崩溃点比错值难定位得多。

### 最小复现（3 条指令）

```json
{"seed":0,"profile":"strict","ops":[["iset",0,-2147483648],["iset",1,-1],["idiv",2,0,1]]}
```

```bash
bash scripts/matrix.sh examples/min-div-overflow.json
```

矩阵末段会给出裁定：四后端的取值并列（wasm/wasm-gc 为 ABORT、js 为回绕值）、
缺口说明，以及 `builtin/intrinsics.mbt:298-309` 的原文引用。

### 工具上的两个连带结论

1. **转录必须有结束哨兵**。没有 `#end <n>` 就说明后端在途中终止，此时已缓冲的输出
   可能整体丢失，转录长度不能当作执行步数。
2. **trap 时步号不可信**。所以矩阵里 `step` 显示 `?` 而不是 `0`，
   真正的步号由 `scripts/localize.py` 前缀二分确定，或由
   `src/oracle` 的静态扫描（`find_static_site`）直接指出。
   这两条都是被这条发现逼出来的设计。

## 发现 1：常量折叠后 NaN 的符号位 —— 实现自由度

**裁定：`IMPLEMENTATION-FREEDOM`，不构成缺陷。**

### 现象

```
(0.0 / 0.0).reinterpret_as_int64()
  wasm / wasm-gc -> 0xFFF8000000000000   （负 quiet NaN）
  js             -> 0x7FF8000000000000   （正 quiet NaN）
```

### 依据

IEEE 754-2019 §6.2.3 不规定 NaN 的符号位；WebAssembly 规范在 NaN propagation
一节把这句话写成了可引用的明文（`exec/numerics.html`）：

> When the result of a floating-point operator other than fneg, fabs, or fcopysign
> is a NaN, then its sign is non-deterministic …

条款说的是「不确定」，所以「两个后端给出不同符号」不构成缺陷。
这一档与 `UNSPECIFIED-DIVERGENCE` 的区别也在这里：**前者是条款写明由实现自选，
后者是条款根本没写**。裁定报告里的 `依据` 与 `原文` 两行就是这句话的落地。

### 为什么仍然值得记录

差异只出现在**编译期常量折叠**：当 `0.0 / 0.0` 是运行期求值时，三个后端都得到
`0xFFF8000000000000`，完全一致。也就是说，同一个表达式在「折叠」与「不折叠」两条
编译路径上会给出不同位模式。

对依赖位序列化的代码——哈希、缓存键、黄金文件比对、跨进程缓存——这会造成
平台相关行为。工程上的正确做法是显式归一化 NaN（本项目在 `semantic` 比较档里折叠掉），
而不是要求各后端统一符号位。

### 复现

两条独立路径都能复现，互相印证：

```bash
# 路径一：常量折叠电池（规格程序模式）
for t in wasm wasm-gc js; do moon run cmd/driver --target $t -- literals | head -1; done

# 路径二：源码探针（普通 MoonBit，不依赖本项目的任何包）
bash scripts/source-probe.sh double-nan-literal
```

24 条常量折叠探针里，**23 条三个后端一致，1 条（`L0 nan_div`）不同**。
源码探针在 CI 的四后端上给出同一结论：`wasm` / `wasm-gc` / `native` 为
`fff8000000000000`，`js` 为 `7ff8000000000000`。也就是说这条差异与后端数量无关，
是 `js` 后端在折叠路径上的独立实现选择。
这条计入回归基线，形如：

```
literals:wasm-vs-js        diff-lines=2
```

（`diff` 输出的一删一增两行；它是基线内的已知量，不是新增问题。）

## 观察 3：`@env.args()` 在 js 上多两个元素

**归类：实现差异，文档已写明，属可预期的平台差异。**

```
moon run ... --target wasm -- alpha "b c"   -> argc = 3
moon run ... --target js   -- alpha "b c"   -> argc = 4
```

js 后端把 `node` 可执行文件与脚本路径也放进了 argv。这对「按 `args[0]` 当作程序名」
的代码是一个陷阱。

**本项目的应对**：`cmd/driver` 与 `cmd/moondiff` 取 argv 的末位元素或扫描子命令名，
不假设固定下标，从而在四个后端上都能取到正确参数。这一条已在 `scripts/selfcheck.sh`
里被间接验证——四个后端跑同一命令，输出必须逐字节一致。

## 尚未覆盖的部分

- **`native` 后端**：本机无 MSVC Build Tools，本地矩阵只有 3 列。
  仓库 CI 在 `ubuntu-latest` 上跑满四后端（Linux 上 native 只需 gcc），
  并用「输出必须是 24 条折叠结果」显式断言 native 真的执行了，而不是被记为 PASS。
- **大整数与高精度小数**：当前原语集只覆盖 32/64 位整数与 f64。
- **并发与 GC 时机**：属非确定性维度，不在本版本差分范围内。
- **未定性的差异**：若 `regress.sh` 出现基线外的新标签，裁定为 `UNDETERMINED` 时
  必须人工对照规范确认，不得直接放宽基线。

## 处置原则

1. **发现的缺陷不自行「修掉」**。差分工具的职责是报告与判定，不是掩盖。
   在 `src/exec` 里加保护让 trap 消失，等于把工具变成安慰剂。
2. **已知差异进基线**。`tests/expected.txt` 记录每一条已定性的结论，
   CI 只对**新增**差异报警。这样既不反复刷屏，也不静默放过。
3. **改动基线必须写明理由**。基线文件里已注明：静默放宽基线等于掩盖差异。
4. **可以上报的照实上报，但说什么要克制**。发现 2 的最小复现与文档边界都已就绪，
   足以提交上游 issue；但诉求是「请补一条规定或确认这是有意设计」，
   而不是「你们违反了自己的规范」——后者正式化之前站不住。
   可直接粘贴的正文见 `docs/UPSTREAM_ISSUE.md`。
